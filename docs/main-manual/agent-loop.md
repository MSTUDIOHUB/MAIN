# Agent 如何工作

MAIN 的 Agent 循环会把每次工作区提交作为一个 Turn，转成一系列可观察步骤：理解目标、读取上下文、调用工具、等待审批、执行验证并输出结论。

## 适用场景

- 想理解 MAIN 为什么会先读文件再回答。
- 需要判断某次工具执行是否正常。
- 想知道模型、本地工具和 UI 审批之间如何配合。

## 前置条件

- 已配置模型。
- 已打开一个会话。
- 如需读写项目，已选择工作区。

## 工作流程

1. MAIN 先为用户提交建立稳定 Turn 身份并持久化接纳信息；Chat 也走这一步。
2. TypeScript 编排层根据当前工作区、会话、场景、工作方式和活跃技能构建上下文，并决定意图、计划和工具策略。
3. 模型判断是否需要工具。只读工具通常自动执行；写入、命令或其他敏感动作按权限进入审批。
4. 已接入统一边界的文件、Shell、PTY 或应用网络请求在 Rust 执行前再次校验工作区、命令结构、目标地址、超时和进程回收规则。
5. 工具结果回到模型上下文，模型继续、恢复、等待审批或给出结论。
6. 执行链通过结构化 Run 事件推进；一个 Turn 最终显示成功、部分完成、受阻、错误或取消中的一种结论。

## 工具来源

MAIN 的工具包括内置工具、技能工具和 MCP 工具。内置工具覆盖文件、搜索、文档、终端、知识库、浏览器验证和 Git 相关能力。技能和 MCP 可以把项目约定、外部引擎或第三方服务接入 Agent 循环。

工具调用本身可能显示 `failed`，例如命令退出码非零或路径不存在。这是该操作的证据，不是整个应用的失败终态。MAIN 会尝试恢复，或把证据整理进 Turn 的错误、受阻或部分完成结论。

## 暂停、取消和结束

- “运行已暂停”表示等待审批、外部状态或显式续跑；目标和进度仍会保留。
- 停止生成会先中止当前 Run，再形成“已取消”的 Run 和 Turn 结论。
- MAIN 不使用“Turn failed”作为结束状态。即使遇到错误，也会给出可读结论并结束该 Turn。

## 步骤

1. 发送任务，并说明期望结果。
2. 观察 MAIN 是否先读取项目上下文。
3. 查看工具块，确认读取、搜索、命令或验证目标是否合理。
4. 遇到审批卡片时，根据 Diff 或命令内容决定接受或拒绝。
5. 任务结束后，检查最终总结是否包含证据、改动和验证结果。

## 结果确认

- 对话中会出现工具执行块，显示工具名、目标和执行状态。
- 长输出会被折叠或截断，避免占满界面。
- 需要你决定时，MAIN 会显示审批卡片、计划卡片或快捷选项。
- 结束时应该只有一个用户可读的最终结论，而不仅是工具日志；刷新或恢复会保留最后一条权威最终答复，并把旧重复项降为过程更新。

## 常见问题

**MAIN 为什么不直接回答，而是先读取文件？**  
因为项目相关问题需要真实上下文。MAIN 的默认策略是先观察再判断，减少凭空猜测。

**工具调用失败是不是模型坏了？**  
不一定。可能是路径不存在、命令失败、MCP 服务未启动、模型工具协议不兼容或权限被拒绝。

**错误发生后为什么 Turn 仍显示“已结束”？**
“结束”说明生命周期已经收口，不等于任务成功。查看结论中的结果类型和工具证据即可区分成功、部分完成、受阻、错误或取消。

**为什么有些思考内容被折叠？**  
MAIN 会把内部思考标签路由到折叠块，把结论和操作说明保留为可见 Markdown。
