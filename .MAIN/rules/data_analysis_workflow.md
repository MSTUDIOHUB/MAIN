# Data Analysis Workflow

当用户的主要目标是“分析数据 / 解读文档 / 生成总结 / 生成报表 Markdown”时，优先遵守以下流程，而不是默认把任务当成代码开发：

## 模式选择
- **Chat**：用于问答、探索式分析、口径澄清、结论说明、汇总结论。
- **Fast**：用于直接产出 `summary.md`、`report.md`、`analysis.md` 等普通 Markdown 报告，或执行轻量数据整理。
- **Plan**：只在任务涉及多阶段数据工程、自动化脚本、报表系统改造、可视化系统实现、跨文件实现或高风险业务逻辑时使用。

## Plan 语义改写
- 数据分析师进入 **Plan** 时，保留 `requirements.md / design.md / tasks.md / bugfix.md` 这套文件名，但其语义必须是“分析计划”，不能默认退化成代码工程计划。
- 推荐映射：
  - `requirements.md`：分析目标、业务问题、数据范围、时间范围、指标口径、交付物、成功标准。
  - `design.md`：分析方法、筛选条件、分组维度、图表/报表结构、验证方式、风险与回退。
  - `tasks.md`：查询、抽样核对、清洗/汇总、交叉验证、生成 Markdown 报告、自动化实现步骤。
  - `bugfix.md`：指标口径错误、数据异常、报表结果不一致、分析链路回归等问题的修复方案。
- 只有任务明确升级为“要写脚本 / 改报表系统 / 搭自动化流水线”时，Plan 的后半段才进入真实实现；否则可以停留在方案、分析或报告设计阶段。
- 不要因为进入 Plan 就自动假设要改源码；先判断用户要的是分析方案、报表方案、自动化方案，还是实际工程实施。

## 工具优先级
- 对 PDF / DOCX / Markdown / TXT 等资料，优先使用 `read_document` 或 `index_workspace_documents`。
- 对 CSV / TSV / XLSX 等大表，优先使用 `analyze_tabular_document` 获取全表概览，再用 `query_tabular_document` 做筛选、聚合、排序或 Top N 查询。
- 只有在需要查看原始行窗口、具体单元格片段或逐段原文时，才进一步使用 `read_document` 分段读取。
- 不要把大型表格整份原文直接塞进上下文后再盲目分析。

## 失败回退规则
- 如果 `analyze_tabular_document`、`query_tabular_document` 或 `read_document` 这类只读工具失败，应在同一轮自动切换到另一个只读策略继续，不要停下来请求用户批准“降级方案”。
- 推荐回退思路：
  - 全表概览失败时，改用结构化查询或分段读取原始行窗口。
  - 聚合查询失败时，先读取相关列的原始数据窗口，再在分析层完成分组、计数或汇总。
  - 单次读取不够时，继续分页/分段读取，直到得到足够证据或确认真实 blocker。
- 只有在以下情况才向用户提问：
  - 文件路径或目标数据不存在；
  - 指标定义、业务口径或时间范围存在实质歧义；
  - 所有只读路径都不足以支持用户问题。
- 避免“进度表演”式文案，例如“我将再次执行查询”“请确认是否同意降级”；应直接继续读取与分析，最后统一汇报结果、限制与下一步建议。

## 输出要求
- 默认输出结构化 Markdown，而不是零散聊天段落。
- 如果用户要“总结”，优先沿用 `.MAIN/templates/report/data_summary.md`。
- 如果用户要“分析报告 / 周报 / 月报 / 诊断报告”，优先沿用 `.MAIN/templates/report/data_analysis_report.md`。
- 如果用户在 Plan 下要的是“分析方案”而不是立即执行，优先让 `requirements.md` / `design.md` 成为可保存、可审阅的方案文档，不要提前把重点转移到代码修改。
- 结论中应明确区分：
  - 已确认事实
  - 推断结论
  - 数据限制 / 口径风险
  - 建议动作

## 边界
- 普通数据分析任务默认不要进入 `.MAIN/plans/`，也不要生成 requirements/design/tasks，除非任务已经明确升级为实施型项目。
- 普通数据分析任务默认不要修改源码，除非用户明确要求开发脚本、报表页面、自动化流程或其他实现工作。
